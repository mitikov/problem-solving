# Завдання 4. Зламайте прототип одним тестом

**Час:** 12 хвилин. **Блок:** 2.4. **Питання:** Е04.

**Мета:** визначати очікування зі специфікації, знаходити дефект контрприкладом і зв’язувати перевірку з потребою.

**Інструмент:** [тренажер](lab.html), вкладка **4. Тести**. Прототипи A–D — програмні навчальні моделі, їхні правила доступні у коді. Не відкривайте код до власної спроби.

## 1. Сплануйте тести — 3 хвилини

Прочитайте правило стенда: **скінченне число 0–100 %; «ПОВНИЙ» за значення ≥85; інакше «Є МІСЦЕ»; непридатне значення → «НЕВІДОМО»; затримка ≤5 с**. `None`, `NaN`, нескінченність, текст, логічні значення та числа за діапазоном є непридатними. Умови й момент відліку — у [сценарії](scenario.md).

Оберіть звичайний, граничний і помилковий входи. Для кожного **до запуску** задайте очікуваний стан; оберіть тип тесту та поясніть, яку частину правила він перевіряє. Перевірка часу застосовується незалежно від правильності стану.

## 2. Знайдіть контрприклади — 4 хвилини

Вибирайте A, B і C, подавайте ті самі входи й натискайте **Випробувати**. Можна натискати картки входів або вводити власні значення. Протокол покаже окремо: чи ваше очікування узгоджене зі специфікацією, чи модель видала потрібний стан і чи вклалася у час.

Знайдіть **хоча б один провальний випадок для кожного з A, B, C**; визначте, яке правило він порушує. Починайте з малої кількості тестів, змінюйте один фактор за раз. Не підлаштовуйте очікування під відповідь прототипу. Звичайний успішний тест не перевіряє всі інші входи.

За бажанням повторіть набір для D. Успіх на обраному наборі не доводить відсутності всіх дефектів і не підтверджує користі для працівника в іншому кабінеті.

## 3. Замкніть три ланцюжки — 3 хвилини

Поверніться до власних Q1–Q3 у картках специфікації. Для однієї вимоги запишіть **три** тести: звичайний, граничний, помилковий. Для двох інших — **по одному**. Кожен має передумову, вхід, дію й очікування, а також ID на кшталт `T1.1 → Q1`.

Якщо ваша Q не стосується індикації рівня, результати стенда не є її перевіркою: складіть відповідний ручний сценарій. Наприклад, вимога про заміну батареї потребує власного сценарію обслуговування. Реальне випробування проводити не потрібно.

## 4. Усуньте неоднозначність — 2 хвилини

Збережіть версію специфікації **до уточнення**. Запишіть одне своє неоднозначне формулювання й точнішу версію. Виправте Q і пов’язаний T, збережіть версію **після уточнення**. Зазначте, які тести зачеплено.

**Необов’язковий раунд:** змініть поріг стенда 85 → 90 %. Прототипи A–D залишаються побудованими для 85 %. Передбачте, які з ваших збережених тестів треба переглянути, задайте нові очікування й повторіть їх. У старих записах поріг лишається 85, нові фіксують 90; вимога може змінитися без автоматичного оновлення реалізації.

<details><summary>Підказка: якщо всі тести проходять</summary>

Шукайте точку зміни правила, значення без показу та правильний стан із запізненням. «Щось показав» не є повним критерієм приймання.

</details>

**Що здати:** журнал із власними очікуваннями; три контрприклади; три ланцюжки R → N → Q → T (щонайменше п’ять власних сценаріїв разом); дві версії уточненої специфікації й пояснення зміни.

**Самоперевірка:** на межі перевірено знак; відсутність показу не названа вільним контейнером; очікування не скопійовано з реалізації; числова відповідність не підміняє перевірку користі.

**Без тренажера:** використайте закриті таблиці спостережень у [ручному маршруті](manual-fallback.md), відкриваючи їх лише після запису очікувань. Позначте виконання як ручну перевірку моделі.
